# LangChain — The Same RAG, Built With a Framework

**LangChain** is a Python library of ready-made building blocks for LLM apps:
prompt templates, chat-model wrappers, retrievers, document loaders, output
parsers, and a way to plug them together into a pipeline (a *chain*).

This project already has a hand-written RAG pipeline (`/documents/ask`). The
LangChain version (`/documents/ask-langchain`) does exactly the same job, so
the two can be compared side by side:

```http
POST /documents/ask            # hand-written
POST /documents/ask-langchain  # LangChain
```

Same request, same response, same Qdrant data, same prompts, same
"I don't know" behavior.

---

## Hand-written vs LangChain

| Step | Hand-written (`AnswerQuestionService`) | LangChain (`LangChainAnswerQuestionService`) |
|---|---|---|
| Retrieve chunks | `embed()` + `vector_store.search()` | `PortsRetriever` (a `BaseRetriever`) |
| Build prompt | OpenAI message dicts | `ChatPromptTemplate` |
| Call the LLM | `OpenAIClient.create_chat_completion` | `ChatOpenAI` |
| Compose the steps | plain Python calls | LCEL chain: `prompt \| llm` |
| Retries / timeouts | own exponential backoff loop | `ChatOpenAI(max_retries=..., timeout=...)` |

---

## The core concepts

### Runnable and LCEL

Every LangChain component is a **Runnable**: it has `invoke()` / `ainvoke()`
(plus `stream()` and `batch()`). Runnables are composed with the pipe operator,
called **LCEL** (LangChain Expression Language):

```python
chain = RAG_PROMPT | chat_model
message = await chain.ainvoke({"system_prompt": "...", "user_prompt": "..."})
```

The output of the prompt (a list of messages) becomes the input of the model.

### Prompt template

```python
RAG_PROMPT = ChatPromptTemplate.from_messages([
    ("system", "{system_prompt}"),
    ("human", "{user_prompt}"),
])
```

Variables in `{...}` are filled in at invoke time.

### Chat model

`ChatOpenAI` wraps the OpenAI API behind a common interface. Switching to
another provider (for example `ChatAnthropic`) only changes this one object.
The rest of the chain stays the same.

### Retriever

A retriever takes a query string and returns a list of `Document`
objects (`page_content` + `metadata`). `PortsRetriever` adapts the project's
own `EmbeddingProvider` and `VectorStore` ports, so it reuses the existing
Qdrant collection and filters instead of creating a second one.

### Output parser

Parsers turn the model output into something else (`StrOutputParser` → plain
string, `PydanticOutputParser` → typed object). This chain keeps the raw
`AIMessage` instead, because it carries the model name and token usage that
the API returns.

---

## When LangChain helps vs adds complexity

**Helps:** swapping providers, standard components (loaders, splitters,
retrievers), streaming/batching for free, tracing with LangSmith, and it is
the foundation for **LangGraph** (the next step: multi-step agent workflows).

**Adds complexity:** extra abstraction layers, frequent API changes between
versions, and harder debugging when something deep in a chain fails. For a
small, stable pipeline, plain code (like `/documents/ask`) is often clearer.
